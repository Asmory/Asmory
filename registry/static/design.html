Design philosophy

Assembly package management should model the machine instead of pretending it does not exist.

Target identityVariantsDead code GCABI contractsLLM-native metadata

Target identity is multidimensional

x86_64 alone is not a useful compatibility promise. An Asmory target combines architecture, ISA baseline/version, required extensions, ABI, object format, OS constraints and toolchain requirements.

Target = arch + ISA baseline + extensions
       + ABI + object format + OS
       + assembler constraints

Package version ≠ machine variant

A semantic version identifies the software release. A Variant identifies a concrete machine implementation. One version may publish AVX2/FMA, AVX-512, NEON and SVE2 variants without abusing version numbers.

fast-gemm 1.4.0
├── x86_64-avx2-fma
├── x86_64-avx512
├── aarch64-neon
└── aarch64-sve2

Let the linker kill dead code

Asmory should not invent a source-level tree shaker. Functions and read-only data should live in granular ELF sections. The linker's existing reachability graph then decides what survives.

.text.gemm_avx2
.text.gemm_avx512
.rodata.gemm_tables

ld --gc-sections

ABI contracts are package metadata

Calling convention, exported symbols, register clobbers, stack alignment and unwind behavior must be machine-readable. “It links” is weaker than “it is safe to call.”

Designed for human + LLM collaboration

LLMs are unusually productive at generating and tuning assembly, but they need explicit constraints. A resolver-readable target contract plus export metadata lets an AI select a compatible package, generate glue code, benchmark variants and iterate without rediscovering the ABI from raw source every time.
